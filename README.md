# Pac-Man

## Description

This project is a full recreation of the classic 1980 arcade game **Pac-Man**, built in
Python 3 on top of the [Arcade](https://api.arcade.academy/) graphics library.

The player navigates a procedurally generated maze, eating pacgums and super-pacgums
while avoiding four autonomous ghosts, across a catalog of increasingly difficult levels.
The game features a full menu flow (main menu, instructions, top highscores, pause,
game over / victory), a persistent highscore board, a JSON-with-comments configuration
file, and a cheat mode intended to speed up peer review.

Maze layouts are **not** generated by this project's own code: they are produced by an
externally assigned *A-Maze-ing* maze-generation package (see [Maze Generation](#maze-generation)).

## Instructions

### Requirements

- Python 3.10+
- Dependencies listed in `requirements.txt` (notably `arcade` and `hjson`)

### Install

```bash
make install
```

### Run

```bash
make run
```

or directly:

```bash
python3 pac-man.py <config_file.json>
```

The program takes **exactly one** argument: the path to a configuration file (see
[Configuration](#configuration)). Any problem with that file (missing file, invalid
JSON, invalid values) is reported with a clear message on the console instead of a
Python traceback, and the game falls back to safe defaults where possible.

### Other Makefile targets

- `make debug` — run the game under `pdb`.
- `make clean` — remove `__pycache__`, `.mypy_cache`, and other build artifacts.
- `make lint` — run `flake8` and `mypy` with the required flags.
- `make lint-strict` — run `flake8` and `mypy --strict`.

| Pause / Resume| SPACE             |
| Menu navigate | Arrow keys / W, S |
| Menu select   | SPACE             |

## Configuration

The game is configured through a JSON file passed as the single command-line
argument. In addition to standard JSON, the file may contain comments (lines starting
with `#`, plus the C/C++ style comments supported by the `hjson` parser used to read
it).

`GameConfig` (in `game_configuration.py`) loads this file and validates its content,
falling back to a safe default and printing a `[Config Warning]` message for any
missing, malformed, or out-of-range value. Unknown keys are ignored. The root of the
file must be a JSON object, otherwise defaults are used entirely.

Recognized keys:

| Key      | Type | Default | Notes |
|----------|------|---------|-------|
| `custom` | bool | `false` | Must be `true` for `lives` and `seed` below to be read from the file at all. |
| `lives`  | int  | `3`     | Clamped to the `[1, 10]` range. Only read when `custom` is `true`. |
| `seed`   | int  | `42`    | Must be `>= 0`. Used to seed the maze generator for the very first level (see below). Only read when `custom` is `true`. |

The remaining gameplay values (screen size, tile size, points per pacgum / super
pacgum / ghost) currently use fixed, sensible defaults defined on `GameConfig`
(`screen_width=900`, `screen_height=900`, `tile_size=60`, `points_per_pacgum=5`,
`points_per_super_pacgum=100`, `points_per_ghost=200`) and are applied identically to
every level.

Example `config.json`:

```jsonc
{
    # Enable custom overrides
    "custom": true,
    "lives": 3,
    "seed": 42
}
```

## Highscore

Highscores are stored persistently as a JSON object (`{"player_name": score, ...}`) in
`highscore.json`, resolved through `persistent_path()` (`paths.py`) so that the file is
written next to the executable when running from a packaged build, and in the current
working directory when running from source — this keeps it writable and durable even
inside a PyInstaller one-file bundle, whose own temp extraction folder is wiped on
exit.

- The file is loaded when the end-of-game screen (`EndGameView`) or the top-highscore
  screen (`TopHighscoreView`) is shown, and it is written back to disk whenever the
  player confirms a name after a win or a loss.
- Loading tolerates a missing file or invalid content: the error is logged and the
  view falls back to an empty highscore table instead of crashing.
- At most 10 entries are kept: once the table already holds 10 names, a new score is
  only added if it beats the current lowest entry, which is then evicted.
- The main menu's "Top Highscore" screen displays the 10 best scores, sorted
  descending.

We chose a flat JSON dictionary of `name -> best score` (rather than a list of
individual runs) because it keeps the file trivial to read and validate, and matches
the "one best score per name" behaviour requested for the highscore board.

## Maze Generation

Maze layouts are produced entirely by the externally assigned *A-Maze-ing* package
(`mazegenerator.py`, `MazeGenerator` class) — this project does **not** implement its
own maze algorithm, and the package is used as-is.

`Maze` (`maze.py`) is our adapter around that package:

- It calls `MazeGenerator(size, perfect=False, entry_cell=..., exit_cell=..., seed=...)`
  and converts the raw wall-bitmask grid it returns into our own `Cell` objects
  (`cell.py`), which know their walls, screen-space center, and pacgum.
- `perfect=False` is used, as required, to allow loops in the maze so that corridors
  stay Pac-Man-compatible instead of forming a strict tree.
- The **first** level is generated with the seed coming from the configuration file
  (`seed`, default `42`) so it is reproducible; every subsequent level passes `seed=0`,
  which the generator interprets as "pick a random seed", producing a different maze
  each time.
- If the generator raises any exception, `Maze._init_grid` wraps it into a
  `MazeGenerationError`, which `Game.load_level` catches to end the game cleanly
  instead of crashing.
- Super-pacgums are placed on the four corner cells of the grid; regular pacgums fill
  every other non-fully-walled cell.

## Implementation

The game is built around Arcade's `View` system: `arcade.Window` swaps between
`MenuView`, `InstructionView`, `TopHighscoreView`, the gameplay `Level` view,
`PauseView`, and `EndGameView` (all in `views.py` / `level.py`), each handling its own
drawing, keyboard, and mouse events.

- **Game loop / orchestration** (`game.py`): `Game` owns a hardcoded catalog of 10
  levels (maze size, time limit, and per-ghost sprite/difficulty/speed), builds the
  `Maze`, `Player`, and `Ghost`s for the current level, and wires up the cheat mode
  before showing the `Level` view. It also handles moving to the next level, victory,
  and game over.
- **Gameplay** (`level.py`): `Level` runs a fixed 60 Hz update loop (via a time
  accumulator) that advances the player and ghosts, checks the level timer, checks for
  level completion (no pacgums left), and handles player/ghost collisions, damage, and
  respawn.
- **Player** (`entity/player.py`): grid-based movement animated as a smooth lerp
  between the current and target cell, direction buffering for responsive turns,
  pacgum/super-pacgum consumption and scoring, and ghost collision resolution
  (damage vs. eating a fleeing ghost).
- **Ghosts** (`entity/ghost.py`): each ghost is a state machine
  (`IDLE`/`MOVE`/`DEAD`/`FLEE`). While chasing, a ghost recomputes a BFS shortest path
  to the player's cell each time it reaches a cell, but only "commits" to
  `difficulty_id` steps of that path before recomputing — a smaller `difficulty_id`
  therefore makes the ghost look less clairvoyant/more erratic, and vice versa. While
  fleeing (after a super-pacgum), it instead paths back toward its spawn corner.
- **UI widgets** (`button.py`, `utils.py`): a lightweight `Button`/`CheckButton` +
  `ButtonGroup` system supporting both mouse hover/click and keyboard
  (`UP`/`DOWN`/`SPACE`) navigation, backed by a simple `HitBox` rectangle for hit
  testing.
- **Cheat mode** (`cheatmode.py`): a panel of `CheckButton`s (skip level, player
  invincibility, freeze all ghosts) shown inside the pause menu to let reviewers
  exercise the game's features quickly.
- **Config & persistence** (`game_configuration.py`, `paths.py`): JSON-with-comments
  config loading with per-field validation and defaulting, and dual path resolution so
  the game behaves the same whether run from source or from a packaged executable.

## General Software Architecture

```
pac-man.py                  Entry point: parses argv, loads GameConfig, starts arcade.Window + Game

game_configuration.py       GameConfig            -> validated runtime settings
paths.py                    resource_path / persistent_path

game.py                     Game                  -> orchestrates menu -> level catalog -> level loop
views.py                    MenuView, PauseView, EndGameView, InstructionView, TopHighscoreView
level.py                    Level (arcade.View)   -> active gameplay view

maze.py                     Maze                  -> builds Cell grid + wall geometry + pacgums
mazegenerator.py            MazeGenerator         -> assigned A-Maze-ing package (external, used as-is)
cell.py                     Cell, Walls
pacgum.py                   Pacgum (+ draw_pacgum)

entity/player.py            Player (arcade.Sprite)
entity/ghost.py             Ghost (arcade.Sprite)

button.py                   Button, CheckButton, ButtonGroup
cheatmode.py                CheatMode, compute_panel_bounds
utils.py                    HitBox
score.py                    ScoreUi
```

High-level relationships:

- `Game` is the composition root: it holds the level catalog, builds a `Maze` and its
  `Player`/`Ghost`s for the current level via `game_configuration.GameConfig`, and
  swaps `arcade.View`s on the window (`MenuView` <-> `Level` <-> `PauseView` <->
  `EndGameView`).
- `Level` depends on `Maze`, `Player`, and a list of `Ghost`, and drives their
  per-frame `update()`.
- `Maze` depends on `MazeGenerator` (external) and owns a grid of `Cell`, each
  optionally holding a `Pacgum`.
- `Player` and `Ghost` both depend on `Maze` (for grid <-> world conversions and
  pathfinding) and on `Cell`/`Walls` for collision/wall checks.
- `views.py` and `level.py` depend on `button.py`/`cheatmode.py`/`utils.py` for their
  UI, and on `paths.py` for reading/writing the highscore file.
